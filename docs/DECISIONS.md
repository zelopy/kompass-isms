# 설계 결정 기록 (ADR)

새 결정은 아래에 번호를 이어 추가한다. 기존 결정을 바꿀 때는 원래 항목을 지우지 말고 상태를 `대체됨(ADR-NNN)`으로 바꾼 뒤 새 항목을 추가한다.

---

## ADR-001 판정은 결정론적 룰 엔진이 한다
- 상태: 채택
- 결정: PASS/FAIL 판정은 코드로 작성한 룰만 내린다. LLM은 판정 이후의 해석, 우선순위화, 조치안 작성만 담당한다.
- 이유: 같은 입력에 같은 결과가 나와야 감사에서 재현성을 설명할 수 있다. LLM 판정은 입력이 같아도 결과가 흔들릴 수 있다.
- 결과: LLM 응답 스키마에 `status` 필드를 두지 않는다. 에이전트도 status를 바꿀 수 없다.

## ADR-002 매핑은 코드와 분리된 데이터로 관리한다
- 상태: 채택 (파일 구조와 확인 표시는 ADR-025로 대체됨)
- 결정: 룰 → KISA 항목 → ISMS-P 통제항목 매핑은 `kompass/mappings/rules.yaml`에 둔다.
- 이유: 매핑은 다대다 관계이고, 가이드 개정이나 기준 추가(CSAP 등) 시 코드 변경 없이 갱신해야 한다.
- 결과: 원문 근거를 확인한 매핑만 `verified: true`로 표시한다.

## ADR-003 수집과 판정을 분리하고 스냅샷을 저장한다
- 상태: 채택
- 결정: collector는 원본 설정을 스냅샷 JSON으로 저장하고, 룰은 스냅샷만 입력으로 받는다.
- 이유: AWS 재호출 없이 재판정이 가능하고, 테스트가 쉬우며, 판정 근거를 보존할 수 있다.
- 결과: 스냅샷은 실제 계정 데이터이므로 `.kompass/`는 커밋하지 않는다.

## ADR-004 읽기 전용을 IAM 정책과 코드 가드로 이중 보장한다
- 상태: 채택
- 결정: 점검 역할은 `SecurityAudit` 관리형 정책으로 제한하고, 코드에서도 botocore 이벤트 훅으로 비읽기 오퍼레이션을 차단한다.
- 이유: 진단 도구가 대상 환경을 변경하는 사고는 신뢰를 잃게 만든다. 에이전트가 도구를 호출하는 4단계에서는 더욱 중요하다.

## ADR-005 권한 오류는 ERROR로 기록한다
- 상태: 채택
- 결정: 수집 실패와 AccessDenied는 PASS가 아닌 `ERROR` 상태다. 단, 설정 미존재 응답(예: 비밀번호 정책 `NoSuchEntity`)은 룰별로 FAIL 처리할 수 있다.
- 이유: "확인하지 못함"을 "양호"로 보고하는 것은 진단 도구의 가장 위험한 오류다.

## ADR-006 Python + uv
- 상태: 채택
- 결정: Python 3.12, uv, pydantic v2, typer, pytest, moto, ruff, mypy strict.
- 이유: boto3·보안 도구 생태계, LLM·RAG 라이브러리 접근성, Prowler SDK와의 호환.

## ADR-007 LLM 공급자 추상화와 마스킹
- 상태: 채택 (3단계 구현)
- 결정: LLM 호출은 공급자 인터페이스 뒤에 두고, 원본 식별정보는 마스킹 후에만 전달한다.
- 이유: 클라우드 설정 데이터를 외부 API로 보내는 것은 실제 조직 도입 시 장애물이 된다. 로컬 LLM 선택지를 열어둔다.

## ADR-008 초기 커버리지는 직접 구현, 확장은 Prowler 어댑터
- 상태: 채택
- 결정: IAM, S3, 보안그룹은 boto3로 직접 구현한다. 이후 커버리지 확장은 Prowler OCSF 출력을 입력으로 받는 어댑터로 해결한다 (5단계).
- 이유: 초기에는 데이터 구조를 직접 다뤄보는 학습 가치가 크고, 이후에는 체크 로직 재작성보다 에이전트 레이어에 시간을 쓰는 것이 프로젝트 목적에 맞다.

## ADR-009 항목 단위 결과는 우선순위 규칙으로 집계한다
- 상태: 채택
- 결정: 리소스 단위 finding을 항목 단위 결과로 집계할 때 `FAIL > ERROR > REVIEW > PASS > N/A` 우선순위를 따른다. ERROR가 섞인 항목은 양호가 될 수 없고 "확인 불가"로 표기한다.
- 이유: 점검표는 항목 단위로 양호/취약을 적는다. 일부 리소스를 확인하지 못했는데 항목을 양호로 적는 것은 ADR-005와 같은 위험이다.
- 결과: 집계 함수는 `models.py`에 두고 우선순위 조합 전체를 테스트한다. 세부 규칙은 `ARCHITECTURE.md`의 "항목 단위 집계".

## ADR-010 사람이 판단할 결과는 REVIEW 상태로 표현한다
- 상태: 채택
- 결정: `Status`에 `REVIEW`를 추가한다. 수집은 자동으로 하되 양호/취약 판단은 사람이 해야 하는 결과(예: IAM-007 그룹 경유 관리자 현황, COVERAGE의 `partial` 항목)에 쓴다.
- 이유: 판단을 미루는 결과를 PASS나 Severity INFO로 표현하면 점검표에서 "양호"로 오인될 수 있다.
- 결과: `REVIEW`는 룰 정의에 따라 결정론적으로만 부여한다. LLM과 에이전트는 어떤 상태도 `REVIEW`로 바꾸거나 `REVIEW`를 해소할 수 없다 (ADR-001).

## ADR-011 내부 심각도와 KISA 중요도를 함께 유지한다
- 상태: 채택
- 결정: 룰의 `Severity`는 5단계(critical~info)를 유지하고, KISA 원문의 중요도(상/중/하)는 `mappings/rules.yaml`의 `kisa_importance`에 원문 그대로 기록한다. 점검표에는 두 값을 별도 칸으로 표시한다.
- 이유: 내부 심각도는 우선순위화에 필요한 해상도를 주고, KISA 중요도는 감사·보고에서 기준 문서와의 대응을 보여준다. 한쪽을 다른 쪽으로 변환하면 원문 근거가 흐려진다.
- 결과: `kisa_importance`는 KISA 항목코드와 마찬가지로 원문 확인 후에만 채운다.

## ADR-012 기준 문서 원문은 커밋하지 않는다
- 상태: 채택
- 결정: KISA 가이드 등 기준 문서 원문 파일(PDF, HWP)은 `.gitignore`로 제외하고, 출처 URL과 SHA-256 해시만 `knowledge/SOURCES.md`에 기록한다.
- 이유: 공개 게시물이라도 공공누리 표시가 없으면 재배포 허락이 명확하지 않다. 링크와 해시만으로 같은 원문을 재현·검증할 수 있고, 대용량 바이너리가 git 기록에 남지 않는다.
- 결과: 항목코드, 항목명, 출처를 밝힌 짧은 인용은 매핑 파일과 문서에 넣을 수 있다. RAG 인덱스(3단계)는 로컬 원문으로 빌드한다.

## ADR-013 partial 항목은 자동으로 양호가 되지 않는다
- 상태: 채택
- 결정: COVERAGE.md에서 `partial`로 분류한 KISA 항목은 룰이 모두 PASS여도 항목 결과를 `REVIEW`(검토 필요)로 둔다. 룰은 명백한 위반만 FAIL로 판정한다.
- 이유: KISA 판단 기준 다수가 "기관 정책에 따라", "주기적으로 검토" 같은 API로 확인할 수 없는 조건을 포함한다. 자동 판정이 이 조건까지 충족했다고 보고하면 확인하지 않은 것을 양호로 보고하는 셈이다 (ADR-005).
- 결과: 상한은 룰이 아니라 항목 집계 단계에서 적용한다. 룰의 PASS는 "검사한 범위에서 위반 없음"이라는 뜻으로 유지되어 증적으로 쓸 수 있다. 항목별 분류는 매핑 데이터에 둔다.

## ADR-014 비밀번호 정책은 KISA CA-04 기준으로 판정한다
- 상태: 채택
- 결정: IAM-004는 영문자·숫자·특수문자 중 2종 조합이면 10자 이상, 3종 조합이면 8자 이상을 요구한다. 대문자와 소문자는 영문자 1종으로 센다.
- 이유: 점검 결과를 KISA 항목에 매핑하는 이상, 판정 기준도 원문(857쪽)과 같아야 한다. AWS 정책의 대·소문자 구분을 그대로 세면 KISA 기준보다 느슨하게 판정된다.
- 결과: 설정 형식은 `password_policy.min_length_two_types`, `min_length_three_types`. 로그인 시도 제한은 IAM에 설정 항목이 없어 자동 확인이 불가능하므로 CA-04는 `partial`이다.

## ADR-015 룰은 하나의 서비스 스냅샷만 본다는 원칙을 유지한다
- 상태: 채택
- 결정: CA-16(버킷 로깅)을 CloudTrail S3 데이터 이벤트로 충족하는 경우라도, S3-005는 `s3` 스냅샷만 보고 판정한다.
- 이유: 룰 간 의존이 생기면 수집 순서, 부분 실패 처리, 테스트 구성이 복잡해진다. 서비스를 엮는 판단은 Interpreter와 Agent의 몫이라는 원래 설계를 지킨다.
- 결과: 데이터 이벤트를 쓰는 조직에서는 S3-005가 FAIL을 낼 수 있다. 4단계 에이전트가 추가 조사로 이를 해석에 반영하되, status는 바꾸지 않는다 (ADR-001).

## ADR-016 1단계 범위에 CloudTrail과 VPC를 추가한다
- 상태: 채택
- 결정: 1단계에 CT-001(CA-13), VPC-001(CA-07), VPC-002(CA-08)를 추가한다. EC2 collector는 보안그룹 전용(`ec2_sg`)에서 `ec2`로 넓혀 VPC·서브넷·라우팅 테이블·네트워크 인터페이스를 함께 수집하고, `cloudtrail` collector를 새로 둔다.
- 이유: 기존 범위는 KISA 클라우드 19개 항목 중 7개만 다룬다. 추가하는 항목 중 CA-13·CA-07은 중요도 "상"이다. 세 룰 모두 읽기 전용 Describe/Get API만으로 판정할 수 있고, 실습 환경에서 비용 부담이 작다.
- 결과: 1단계가 다루는 KISA 항목은 10개가 된다. VPC 룰은 같은 `ec2` 스냅샷 안에서 판정하므로 ADR-015와 충돌하지 않는다.

## ADR-017 "기관 정책" 조건은 설정으로 표현되면 자동 판정한다
- 상태: 채택
- 결정: KISA 판단 기준의 "기관 정책에 따라"가 설정값(읽기 이벤트 기록 여부, 보존 기간 일수 등)으로 표현되는 경우 `kompass.yaml`로 기관 기준을 받아 판정하며, 그 항목은 `full`로 분류할 수 있다. 주기적 검토 수행이나 업무상 필요성처럼 설정으로 표현되지 않는 조건이 있으면 `partial`이다.
- 이유: "기관 정책"이라는 표현만으로 `partial`로 분류하면 API로 충분히 판정할 수 있는 항목(CA-13, CA-16)까지 자동으로 양호가 나오지 않는다. 반대로 정책 내용을 임의로 가정하면 판정 근거가 흐려진다.
- 결과: 기본값은 일반적인 권고 수준으로 두고, 보고서에 적용한 기준값을 함께 표시한다. CA-13과 CA-16은 `full`을 유지한다.

## ADR-018 기본 보안그룹 규칙은 KISA CA-09에 매핑하지 않는다
- 상태: 채택
- 결정: SG-004는 KISA 매핑에서 빼고 ISMS-P(2.6.1)에만 매핑한다. FAIL은 네트워크 인터페이스가 연결된(사용 중인) 기본 보안그룹에 규칙이 있을 때만 낸다.
- 이유: AWS는 모든 VPC의 기본 보안그룹에 기본 규칙을 만든다. 이를 CA-09 "불필요한 규칙"으로 보면 손대지 않은 계정에서도 리전마다 FAIL이 나와 CA-09가 항상 취약이 되고, 실제 개방 위험(SG-001~003)이 묻힌다. 매핑 근거도 원문의 직접 언급이 아닌 해석이었다.
- 결과: CA-09는 SG-001~003만으로 판정한다. 기본 보안그룹 정리는 ISMS-P 관점의 개선 권고로 보고한다.

## ADR-019 모델은 깊은 수준까지 불변이고, 데이터는 JSON 호환 형태로 정규화한다
- 상태: 채택
- 결정:
  - `Snapshot.data`와 `Finding.evidence`는 생성 시 JSON으로 한 번 왕복시켜 원본과 분리된 JSON 호환 dict로 만든다. JSON으로 표현할 수 없는 값은 생성 시점에 거부한다.
  - 시퀀스 필드는 튜플이다. 시각 필드는 시간대가 있는 값만 받고 UTC로 맞춘다.
  - `model_copy(update=...)`를 막는다. 매핑은 `Finding.with_mappings()`로만 붙이며, 이 메서드는 전체 필드를 다시 검증한다.
  - `rule_id`는 `^[A-Z][A-Z0-9]*-\d{3}$` 형식만 받는다.
  - 항목 집계 함수는 `automation` 인자를 필수로 받는다.
- 이유: 1차 구현 검토에서 재현된 문제들이다. boto3의 `datetime`이 저장 후 문자열로 바뀌어 바로 수집한 스냅샷과 저장된 스냅샷에서 룰이 다르게 동작할 수 있었고(ADR-003 위반), `model_copy`로 status를 바꿀 수 있었으며(ADR-001 위반), 증적 내부를 생성 후 수정할 수 있었다. 집계 함수의 기본값(full)은 분류를 빠뜨리면 partial 항목을 양호로 만들었다(ADR-013 위반).
- 결과:
  - 룰은 스냅샷의 날짜를 항상 문자열로 받고 공용 함수로 파싱한다.
  - 보고서는 UTC로 저장된 시각을 표시할 때 KST로 변환한다.
  - `data`·`evidence` dict 자체는 파이썬에서 완전히 얼리지 않는다. 생성 시 복사로 원본과 분리하고, 생성 후 수정하지 않는 것은 코드 규칙으로 지킨다.
  - 5단계 Prowler 어댑터의 체크 ID(`s3_bucket_public_access` 등)는 이 형식을 통과하지 못한다. 어댑터 구현 시 출처 접두사(예: `PROWLER:...`)를 허용하도록 형식을 확장할지 결정한다.

## ADR-020 읽기 전용 가드에 sts:AssumeRole만 예외로 허용한다
- 상태: 채택
- 결정: 가드 허용 목록에 `sts:AssumeRole` 하나를 서비스·오퍼레이션 이름이 모두 일치할 때만 허용한다. `AssumeRoleWithSAML`, `AssumeRoleWithWebIdentity`, `AssumeRoot`나 다른 서비스의 같은 이름은 허용하지 않는다.
- 이유: 조직에서는 계정마다 점검 전용 역할을 두고 AssumeRole로 들어가는 방식이 일반적이다. AssumeRole은 대상 계정의 설정을 바꾸지 않고 임시 자격증명만 발급받는다. botocore의 역할 자격증명 공급자도 가드가 걸린 세션의 이벤트 훅을 거치므로, 허용하지 않으면 역할 기반 프로필을 쓸 수 없다.
- 결과: CLAUDE.md 원칙 2에 예외를 명시한다. 허용 목록을 늘리는 이후의 변경도 사용자 확인 후 ADR로 기록한다. 역할에는 여전히 `SecurityAudit`만 부여한다 (ADR-004).

## ADR-021 점검 세션은 프로필 기반이며, 세션 단계 실패는 실행을 중단한다
- 상태: 채택
- 결정:
  - `open_scan()`이 가드 세션, 계정 ID, 파티션, 호출자 ARN, 기본 리전, 점검 리전을 `ScanContext`로 묶고, collector는 이것만 받는다.
  - 자격증명은 AWS 프로필(액세스 키 또는 역할 프로필)로만 받는다. `--role-arn`처럼 kompass가 직접 AssumeRole을 호출하는 방식은 두지 않는다. SSO 프로필은 1단계에서 지원하지 않는다.
  - 기본 리전이 없으면 중단한다. `--regions`의 알 수 없거나 비활성인 리전은 점검 전에 거부한다.
  - 세션 단계 실패(자격증명·프로필·리전·`GetCallerIdentity`·`DescribeRegions`)는 finding을 만들지 않고 `SessionError`로 중단한다.
  - `--regions`는 리전 리소스에만 적용하고, S3 버킷은 리전과 관계없이 모두 점검한다.
- 이유:
  - 역할 프로필은 botocore가 자격증명 갱신까지 처리하므로 장시간 점검에도 안전하고, 가드 통과도 확인했다. 직접 AssumeRole을 구현하면 만료 처리를 다시 만들어야 한다.
  - SSO 토큰 갱신(`sso-oidc:CreateToken`)은 가드 허용 목록 밖이라 점검 도중 막힐 수 있다 (미검증).
  - 리전을 몰래 대체하거나 잘못된 리전으로 진행하면, 결과 전체가 ERROR로 채워지거나 다른 파티션에서 틀린 결과가 나온다.
  - 계정 ID를 모르면 스냅샷을 만들 수 없으므로 세션 실패는 ERROR finding으로 표현할 대상이 아니다. ADR-005는 개별 API 수집 실패에 적용한다.
  - 공개 버킷은 어느 리전에 있든 위험하다. 리전 범위를 좁혔다고 다른 리전 버킷을 빼면 중요한 취약점을 놓친다.
- 보완 (구현 검토 반영): 리전 인자 문자열 오용 차단, 상태 필드가 없는 리전은 활성으로 포함, 기본 리전 연결 실패는 리전 확인 안내로 구분, client 기본 설정(standard 재시도·10초 연결 대기·`kompass/<버전>` 요청 식별자), `expected_account_id`로 대상 계정 확인.
- 결과: 실습 계정에서 활성 리전 17개(moto는 38개, opt-in을 구분하지 않음)를 확인했다. opt-in 판별은 순수 함수로 분리해 가짜 응답으로 테스트한다. 테스트는 `tests/conftest.py`가 개발자 PC의 실제 AWS 설정을 가린 상태에서만 실행된다.

## ADR-022 스냅샷은 계정별 점검 폴더에 저장하고, 완료 표시와 해시로 무결성을 확인한다
- 상태: 채택
- 결정: 스냅샷은 `.kompass/snapshots/<account_id>/<scan_id>/<service>.json`에 저장한다. 점검 정보와 파일별 SHA-256을 담은 `scan.json`(`ScanManifest`)을 맨 마지막에 쓰고, 불러올 때 해시를 대조한다. `scan_id`는 UTC 시각에 무작위 접미사를 붙인다. 저장 위치에는 `*`만 담은 `.gitignore`를 자동으로 만든다.
- 이유:
  - 같은 초에 점검을 두 번 하면 시각만으로는 폴더가 겹친다.
  - 계정 ID가 경로에 없으면 여러 계정을 점검할 때 "최신 스냅샷"이 다른 계정 것이 될 수 있다.
  - 완료 표시가 없으면 중단된 점검을 정상 점검처럼 불러와 일부 서비스가 빠진 결과를 낼 수 있다.
  - 스냅샷은 판정 근거(증적)이므로 저장 후 손상·수정 여부를 확인할 수 있어야 한다.
  - 저장소 밖에서 실행하면 `.kompass/`가 다른 git 저장소에 커밋될 수 있다 (원칙 4).
- 결과: 해시는 우발적 손상과 단순 수정을 찾는 장치이며, `scan.json`까지 고치는 의도적 위조는 막지 못한다. 위조 방지가 필요해지면 서명을 별도로 검토한다.

## ADR-023 룰 실행기는 누락과 룰 버그를 숨기지 않는다
- 상태: 채택
- 결정:
  - 스냅샷이 없는 서비스의 룰은 건너뛰고 "건너뛴 룰" 목록으로 돌려준다.
  - 룰은 항상 finding을 하나 이상, 자기 ID로만 내야 하며, 어기면 실행을 중단한다.
  - 룰 코드의 예외는 잡지 않는다.
  - 룰은 `evaluate(snapshot, settings)`로 판정 기준값을 받는다. 설정은 정의되지 않은 키를 거부한다.
- 이유: 수집하지 않은 서비스를 PASS로 처리하거나, finding이 비어 항목이 "점검하지 않음"과 구분되지 않거나, 룰 버그가 ERROR로 묻히면 모두 "확인하지 못한 것을 양호로 보고"하는 쪽으로 기운다 (ADR-005). 설정 오타가 조용히 기본값으로 바뀌면 사용자가 의도한 기준과 다른 판정이 나온다.
- 결과: 룰 하나의 버그가 점검 전체를 중단시킬 수 있다. 대신 단위 테스트에서 바로 드러난다. 룰 ID·제목과 RULES.md의 일치는 테스트로 강제한다.

## ADR-024 IAM 판정은 수집 시각 기준이며, 확인할 수 없는 이력은 양호로 보지 않는다
- 상태: 채택
- 결정:
  - IAM-005·006·008의 경과 일수는 판정 시각이 아니라 스냅샷 수집 시각을 기준으로 계산한다.
  - 루트 `password_last_used`가 `no_information`이면 IAM-008은 REVIEW다.
  - Identity Center가 만든 역할(`/aws-reserved/sso.amazonaws.com/`)이 있으면 IAM-009는 REVIEW다.
  - Identity Center 인스턴스는 활성 리전 전체에서 조회한다 (`ScanContext.enabled_regions`).
- 이유:
  - 판정 시각을 기준으로 하면 같은 스냅샷을 다른 날 다시 판정했을 때 결과가 바뀐다 (ADR-001, ADR-003).
  - 실습 계정에서 루트로 로그인한 직후에도 `no_information`이었다. 이를 "사용 안 함"으로 보면 거짓 PASS가 된다 (ADR-005).
  - 조직 멤버 계정에서는 Identity Center 인스턴스가 관리 계정에 있어 조회되지 않는다. 역할을 보지 않으면 외부 IdP 로그인이 있는데도 N/A가 된다.
  - 인스턴스는 한 리전에만 있으므로 점검 리전을 좁히면 놓친다.
- 결과: IAM-008은 많은 계정에서 REVIEW로 나올 수 있다. CA-02는 원래 partial이라 항목 결과에는 영향이 없다.

## ADR-025 매핑은 항목·룰·ISMS-P 세 파일로 나누고, 보고서를 만들 때 붙인다
- 상태: 채택 (ADR-002의 파일 구조를 대체)
- 결정:
  - `kisa_items.yaml`(KISA 항목 속성), `rules.yaml`(룰 → KISA 항목, 룰별 ISMS-P 후보), `isms_p_controls.yaml`(별표 7의 101개 통제항목)로 나눈다.
  - 확인 여부를 `kisa_verified`와 `isms_p_verified`로 나눈다. `Mappings` 모델도 같다.
  - 매핑은 `findings.json`에 넣지 않고 보고서를 만들 때 붙인다. 보고서에 매핑 파일의 SHA-256을 남긴다.
  - 매핑 데이터는 RULES.md, COVERAGE.md, 룰 레지스트리, 별표 7 항목 목록과 테스트로 대조한다.
- 이유:
  - 중요도와 자동화 분류는 KISA 항목의 속성이다. 룰마다 적으면 같은 항목에 묶인 룰끼리 값이 어긋날 수 있다.
  - KISA 매핑은 사용자가 확인했고 ISMS-P는 초안이라, 하나의 `verified`로는 상태를 표현할 수 없다.
  - ISMS-P 매핑은 앞으로 고칠 가능성이 크다. 판정과 분리하면 다시 판정하지 않고 보고서만 다시 만들 수 있다.
- 결과: ISMS-P 항목명은 안내서 항목 제목에서 옮기고, 번호는 별표 7과 대조했다 (101개 일치).

## ADR-026 항목 단위 결과에 "미구현"과 "점검하지 않음"을 두고, ISMS-P는 자동으로 양호가 되지 않는다
- 상태: 채택
- 결정:
  - KISA 항목·ISMS-P 통제항목 결과(`ItemOutcome`)에 `Status` 값 외에 `NOT_IMPLEMENTED`(담당 룰 없음, 수동 점검)와 `NOT_EVALUATED`(담당 룰을 건너뜀)를 둔다.
  - 담당 룰 중 일부만 건너뛰었으면 확정된 FAIL이 있을 때만 FAIL, 아니면 `NOT_EVALUATED`다.
  - ISMS-P 통제항목은 관련 룰이 있어도 항상 partial로 집계한다.
- 이유:
  - 담당 룰이 없거나 실행되지 않은 항목을 "해당 없음"(N/A)으로 표시하면 "점검 대상 리소스가 없음"과 구분되지 않는다 (ADR-005).
  - ISMS-P 통제는 정책·절차·검토 같은 관리 요소를 포함한다. 클라우드 설정 점검만으로 통제항목 충족을 단정할 수 없다.
- 결과: 실습 계정에서 KISA 19개 항목 중 10개가 자동 판정, 9개가 수동 점검으로 표시된다. ISMS-P 101개 중 89개는 자동 점검 범위 밖이다.

## ADR-027 결과는 저장소 최상위의 reports/ 한곳에 저장한다
- 상태: 채택 (ADR-022의 저장 위치를 대체, 사용자 요청 2026-10-14)
- 결정:
  - 기본 저장 위치는 `--store` → `KOMPASS_STORE` 환경 변수 → 현재 폴더에서 위로 찾은 kompass 저장소(`pyproject.toml`의 `name = "kompass-isms"`) 최상위의 `reports/` → 현재 폴더의 `reports/` 순서로 정한다.

## ADR-028 리전 전체가 접근 거부되는 리전은 점검 범위에서 빼고 보고서에 명시한다
- 상태: 채택 (사용자 결정, 2026-10-14)
- 결정:
  - `--regions`를 지정하지 않으면 점검 시작 시 리전마다 `ec2:DescribeVpcs`를 한 번 시도한다. 기본 리전은 되는데 `AccessDenied`·`AccessDeniedException`·`UnauthorizedOperation`으로 거부되는 리전은 점검 범위에서 뺀다.
  - 기본 리전까지 거부되면 아무 리전도 빼지 않는다. 연결 실패 같은 다른 오류도 빼지 않는다. 직접 지정한 리전은 확인하지 않는다.
  - 뺀 리전과 거부 메시지는 `ScanContext.excluded_regions`, `scan.json`의 `excluded_regions`, 보고서 점검 정보에 "점검 범위 밖"으로 남기고, 실행 화면에 경고한다.
- 이유:
  - 리전 제한 SCP를 쓰는 조직에서는 막힌 리전마다 EC2 룰이 ERROR를 내 KISA 항목이 "확인 불가"가 되어 점검표가 쓸모없어진다.
  - SCP는 보통 관리자 역할을 예외로 두므로 막힌 리전에도 리소스가 있을 수 있다. 그래서 "해당 없음"이 아니라 범위 밖으로 명시한다. 양호로 오해되지 않게 하는 것이 핵심이다 (ADR-005).
  - 점검 권한 자체가 없으면 모든 리전이 거부된다. 이때 리전을 빼면 EC2 점검이 조용히 통째로 사라지므로 기본 리전 거부 시에는 빼지 않는다.
  - SCP 거부 메시지 형식은 조직 환경이 없어 확인하지 못했다. 그래서 메시지 내용이 아니라 거부 오류 코드와 기본 리전 대비로 판별한다.
- 결과: 시도 호출을 동시에 보내 실습 계정(17개 리전) 기준 세션 시작이 2.5초 걸린다 (차례로 보내면 23.8초).

## ADR-029 3단계 LLM 해석의 모델·원문 조회·호출 단위
- 상태: 채택 (사용자 결정, 2026-10-14)
- 결정:
  - 모델은 Claude Opus 5.5(`claude-opus-5-5`)이며 effort는 `kompass.yaml`로 조정한다. 공급자 인터페이스 뒤에 두어 로컬 LLM 구현체를 붙일 자리를 남긴다 (ADR-007).
  - 원문 조회는 벡터 검색이 아니라 항목 코드로 한다. PDF를 KISA 항목(CA-01~19)·ISMS-P 통제항목(101개) 단위로 잘라 로컬 색인(JSON)을 만들고, finding에 매핑된 코드로 본문을 꺼낸다. Chroma 벡터 검색은 자유 질문이 필요한 4단계로 미룬다.
  - 색인 생성 스크립트는 `uv run --with pypdf`로 실행하며 pypdf를 프로젝트 의존성에 넣지 않는다. 색인은 원문을 담으므로 커밋하지 않는다 (ADR-012).
  - 해설은 조치가 필요한 finding(FAIL·ERROR·REVIEW)을 룰 단위로 묶어 한 번에 요청한다.
  - 의존성은 `anthropic`만 추가한다.
- 이유:
  - 각 finding의 KISA·ISMS-P 코드는 매핑으로 이미 정해져 있다. 코드로 조회하면 검색 오류가 없고 인용 검증(코드·구절이 원문에 있는가)이 단순하며, 무거운 의존성(chromadb, 임베딩 모델)이 필요 없다.
  - 룰 단위로 묶으면 같은 원문을 반복해 보내지 않아 비용이 줄고(실습 계정 기준 호출 28회 → 약 12회), 같은 룰의 해설이 일관된다.
- 결과: PLAN.md의 RAG 항목을 "항목 코드 단위 색인"으로 바꾼다.

## ADR-030 LLM 공급자 호출 방식과 설정 위치
- 상태: 채택 (2026-10-14)
- 결정:
  - Claude 요청은 구조화된 출력(`beta.messages.parse`, `output_format=RuleExplanationDraft`)으로 받는다. 응답 스키마에는 `status`·`severity` 필드가 없다 (원칙 1, 테스트로 검사). 우선순위(`priority`)는 LLM의 의견이며 룰의 severity를 바꾸지 않는다.
  - 안전 분류기 거부 시 서버 측 대체 모델(`fallbacks="default"`, beta `server-side-fallback-2026-07-01`)을 기본으로 켠다. 실제로 답한 모델과 대체 여부를 남긴다. 대체 모델까지 거부하면 `LLMRefusal`.
  - 모델·effort·max_tokens는 `kompass.yaml`의 `llm` 섹션에 둔다 (기본 `claude-opus-5-5`, effort `high`, 16000). LLM 설정은 판정 기준값이 아니므로 findings 파일의 `settings`에서 뺀다 (`Settings.judgment_criteria()`).
  - API 키는 환경 변수 `ANTHROPIC_API_KEY`로만 받는다. 설정 파일에 키 항목을 두지 않는다.
  - 실제 API를 부르는 테스트는 `llm` 마커로 기본 실행에서 제외한다 (`pytest -m llm`). 보내는 내용은 가공한 가짜 finding뿐이다.
- 이유: 판정과 해설 설정을 한 파일에서 관리하되, 판정 재현 정보에 판정과 무관한 값이 섞이지 않게 한다. effort는 인용 정확도를 위해 모델 기본값(medium)보다 높게 잡고, 비용이 문제면 설정으로 낮춘다.

## ADR-031 해설 명령과 보고서 반영 방식
- 상태: 채택 (2026-10-14)
- 결정:
  - `kompass explain`은 최근(또는 지정한) 판정 결과를 해설한다. 요청 전에 대상(룰·finding 수)과 예상 비용을 보여주고 확인을 받는다. `--yes`로 확인을 건너뛰고, `--dry-run`은 비용만 보여주고 끝낸다. 예상 비용은 토큰 계산 API로 센 입력 토큰과 룰당 출력 4,000 토큰 가정으로 어림한다 (재시도 제외).
  - 해설은 `reports/explanations/<계정>/<점검 ID>.explanations.json`에 판정 결과와 따로 저장한다. 보고서는 해설의 `findings_evaluated_at`이 판정 결과의 판정 시각과 같을 때만 붙인다. 다시 판정했으면 붙이지 않고 경고한다.
  - 보고서에는 "AI 해설 (참고)" 절(Markdown)과 시트(Excel, 해설이 있을 때만)를 두고, 판정을 바꾸지 않는다는 안내와 검증 상태(검증됨·검증되지 않음·해설 실패)를 함께 표시한다.
  - LLM이 쓴 문장은 신뢰하지 않는다. Markdown에서는 줄바꿈을 접고 HTML을 이스케이프하며, 코드 블록 펜스는 본문의 백틱보다 길게 잡는다. Excel은 기존 수식 주입 방지를 그대로 거친다.
  - 룰 하나의 LLM 오류는 그 룰만 실패로 기록하고 계속한다. 모든 룰이 실패하면 종료 코드 5.
  - 시스템 프롬프트는 `kompass/interpreter/explain_system.txt`에 둔다.
- 이유: 비용이 드는 호출은 사용자가 규모를 보고 결정하게 한다. 판정 결과와 해설의 짝이 어긋나면 다른 finding을 설명하는 해설이 보고서에 섞일 수 있다.

## ADR-032 마스킹 보강과 전송 직전 검사 (노출 사고 대응)
- 상태: 채택 (사용자 승인, 2026-10-14)
- 배경: 실습 결과로 프롬프트를 로컬에서 다시 만들어 검사한 결과, 첫 두 번의 실제 해설 실행에서 S3 버킷 이름 4개와 서브넷 ID 1개가 마스킹되지 않은 채 전송되었다 (대상은 삭제한 실습 계정). 원인: (1) 이름을 증적의 일부 키에서만 모았고 S3 finding은 버킷 이름이 `resource`에만 있음, (2) 다른 finding의 이름이 증적에서 참조됨, (3) dict 키를 마스킹하지 않음, (4) 리소스 ID 패턴이 이름 속 `-acl-0e094f74`를 잘라 이름 치환이 실패함. 테스트 데이터가 실제 증적 형태와 달라 드러나지 않았다.
- 결정:
  - 이름은 보고서 전체 finding의 `resource`·이름 키·`log_target_for`·`group:`/`inline:` 접두 값·ARN 경로 구간에서 모은다. `account`, `default`는 이름으로 보지 않는다.
  - 치환 순서를 ARN → 이름 → 리소스 ID → IAM 고유 ID(`AIDA`·`AROA`·`AKIA` 등) → 계정 ID → IP로 바꾸고, 리소스 ID는 앞뒤가 이름 문자이면 잡지 않는다. dict 키도 마스킹한다.
  - ARN은 리소스 종류(첫 구간)만 남기고 경로 구간을 모두 바꾼다 (AWS가 정한 구간·리전은 남김). S3 ARN은 전부 바꾼다.
  - 보내기 직전에 검사해 원본 `resource` 값, 일부만 바뀐 값, 남은 이름이 있으면 그 룰은 보내지 않고 실패로 기록한다 (fail closed). 오류 메시지에는 원본 값을 넣지 않는다. `--dry-run`의 토큰 계산 요청도 같은 검사를 거친다.
  - 실제 증적 형태의 회귀 테스트를 둔다. 실제 판정 결과가 있으면 프롬프트를 로컬에서 재구성해 노출을 검사한다.
  - 같은 문서 항목의 절반 넘게 나오는 형식 문구(예: "조치 시 영향 일반적인 경우 영향 없음")는 근거 인용으로 인정하지 않는다.
- 결과: 같은 실습 결과로 재검사해 노출 0건, 전송 차단 0건을 확인했다.

## ADR-033 해설 평가셋 설계
- 상태: 채택 (사용자 결정, 2026-10-14)
- 결정:
  - 평가 대상은 `kompass explain`의 룰별 해설 흐름(`explain_report`) 하나다. 룰 판정은 `lab/expected.yaml`이 담당하므로 범위 밖이다. 케이스 하나 = 룰 묶음 하나(실제 LLM 호출 단위).
  - 케이스는 실습 결과 16개 룰 묶음을 가공(계정 ID·IP·리소스 ID·이름 접미사를 가짜 값으로, 구조·개수·상태는 유지)한 것과, 실습에 없던 상황을 보강한 약 20개로 만든다. 가짜 데이터만 커밋한다 (원칙 4).
  - 채점은 결정론 지표만 쓴다 (LLM 판정자 없음): 검증 통과(헤드라인), 첫 응답 통과, 인용 정밀도, 핵심 근거 인용, CLI 문법 유효율(botocore 서비스 모델), 조치 작업 포함, 대상 리소스 일치, 안전 지표(식별정보 노출·지어낸 자리표시자·문체 위반). 정답의 근거 구간은 `(항목코드, 구간 이름)`으로만 적고 원문은 실행 시 로컬 색인에서 꺼낸다 (ADR-012).
  - Terraform 수정안은 실행·문법 검사 없이 제시 여부와 리소스 종류 일치만 기록한다 (원칙 6 취지).
  - 위치: 채점·로더 `kompass/evals/`, 케이스·정답 `evals/explain/`(커밋), 실행기 `scripts/run_explain_eval.py`, 결과 `.claude/hillclimb/explain/<variant>/`(results.jsonl·traces·errors.jsonl, traces와 보고서는 커밋 안 함).
  - 실행기는 실제 `explain_report`를 호출하고 공급자를 기록용 래퍼로 감싼다. 동시 실행, 요청별 시간 제한(`llm.timeout_s`, 실행 중인 스레드는 멈출 수 없어 실행기 수준 마감은 두지 않음), (케이스, 반복) 단위 재개, 실패 분류(거부·시간 초과·API 오류·전송 차단), 응답 모델 확인, dry-run 비용 추정을 갖춘다. 반복 2회.
  - 유료 실행 전에 오라클(정답 해설 → 약 100%)과 널(빈 해설 → 약 0%)을 pytest로 확인한다. 케이스 목록과 파일럿 채점 결과는 각각 사용자 승인을 받는다.
- 이유: 지표가 무료·재현 가능해야 프롬프트나 모델을 바꿀 때마다 돌릴 수 있다. 설명의 사실 일치처럼 판단이 필요한 지표는 판정자 검증 비용이 커서 2차로 미룬다.
- 기준선 결과 (2026-10-14, claude-opus-5-5 effort high, 40개 × 2회, 약 $5.2): 검증 통과·첫 응답 통과·인용 정밀도·핵심 근거·CLI 유효·대상 일치·안전 지표 모두 100%, 조치 작업 99.4% (1건: 조회 권한이 없던 리전에 대한 조치 누락). `.claude/hillclimb/explain/baseline/metrics.md`.
- 해석: 현재 모델·프롬프트에서 지표가 거의 포화되어 있다. 이 평가셋은 품질 개선 측정보다 **회귀 검출용**(프롬프트·모델·마스킹을 바꿨을 때 점수가 떨어지는지)으로 쓴다. 개선 측정이 필요해지면 더 어려운 케이스(다중 리전 ERROR, 정책 해석이 필요한 IAM 등)를 보강한다.
- 평가셋이 찾은 결함: 마스킹 자리표시자 번호 10 이상을 "일부만 가려짐"으로 오판해 요청을 모두 차단하던 버그(수정), 채점기 오판 4종(CLI 불리언 구조체 플래그, 관련 리소스 대상, 구간 이름을 포함한 인용, 계정 단위 변경 — 모두 수정, `--regrade`로 재채점), 보강 케이스의 S3 오류 작업 이름이 실제 수집기 형식과 달랐던 문제(수정 후 해당 케이스 재실행).

## ADR-034 종합 위험 평가
- 상태: 채택 (사용자 결정, 2026-10-14)
- 결정:
  - 룰별 해설이 끝나면 보고서 전체에 대해 LLM을 한 번 더 호출해 여러 finding이 겹쳐 생기는 위험 시나리오와 조치 순서를 만든다 (`interpreter/assessor.py`, `assess_system.txt`). `kompass explain`에 포함되며 `--no-assessment`로 끈다. 예상 비용에도 1회를 더한다.
  - 입력은 해설 대상 finding 전체(최대 60건, 마스킹)와 룰별 해설의 우선순위·요약(같은 마스커로 다시 가림)이다. 원문은 다시 보내지 않는다. 전송 직전 차단 검사(`Masker.require_clean`)를 똑같이 적용한다.
  - 응답 스키마(`RiskAssessmentDraft`)에는 status가 없다. 검증: 시나리오의 finding 키가 보낸 finding에 있다, 조치 순서에 해설 대상 룰이 모두 정확히 한 번씩 있다, 지어낸 자리표시자가 없다. 문제가 있으면 한 번 다시 묻고 그래도 있으면 "검증되지 않음". 실패해도 룰별 해설은 남는다 (`assessment_failure`).
  - 보고서: Markdown "AI 해설" 절 맨 앞에 "종합 위험 평가", Excel "AI 종합 평가 (참고)" 시트, 점검 정보에 검증 상태.
  - 평가셋 실행기는 룰별 해설만 측정하므로 종합 평가를 끈다. 종합 평가의 평가는 다음 과제다.
- 이유: 룰별 해설만으로는 "전체 개방 보안그룹이 공인 IP 인터페이스에 붙어 있음"처럼 룰을 넘는 위험이 드러나지 않는다. 참조 무결성은 코드로 검증할 수 있어 원칙 1·5를 지키면서 LLM의 종합 능력을 쓴다.
- 실제 확인 (2026-10-15, 실습 결과, claude-opus-5-5): 첫 실행은 전송 직전 검사에 걸려 차단되었다 (룰별 해설 요약 속 "vpc-…의"처럼 한글 조사가 붙은 리소스 ID를 마스킹하지 못하던 버그, 수정). 수정 후 종합 평가는 첫 시도에 검증을 통과했다 (시나리오 9개, 조치 순서 16개 룰 전부, $0.17). 같은 버킷에 걸린 S3-001·002·003·005를 한 시나리오로 묶고, RestrictPublicBuckets로 막힌 버킷과 미연결 보안그룹을 잠재 위험으로 구분했다.
- 보완 (2026-10-15 검토): 종합 평가만 실패했을 때 룰별 해설을 다시 만들지 않도록 `kompass explain --assessment-only`를 둔다. 같은 판정 결과의 저장된 해설을 재사용하고 사용량·비용은 기존 합계에 더한다. 예상 비용에는 아직 없는 룰별 요약 분량(룰당 약 250토큰)을 더한다.
- 알려진 한계 (ADR-032 전송 직전 검사): 리소스 값을 부분 문자열로 찾으므로 `logs`처럼 짧고 흔한 이름은 다른 단어 속에서도 걸려 그 요청이 차단될 수 있다. 안전한 쪽(보내지 않음)으로 틀리므로 그대로 둔다.

## ADR-035 4단계 에이전트 구조
- 상태: 채택 (사용자 결정, 2026-10-15)
- 결정:
  - 에이전트 루프는 Anthropic SDK의 도구 러너(tool runner, 베타)로 만들고 공급자 인터페이스 뒤에 둔다 (테스트는 가짜 공급자, 로컬 LLM 자리 유지). 반복 상한·로그는 러너의 반복마다 처리한다.
  - 도구는 목적별 읽기 도구 10개 내외로 정한다 (범용 "아무 읽기 API" 도구는 두지 않는다). 도구마다 반환 필드와 식별자 필드를 선언해 필드 단위로 마스킹하고, 필요 없는 자유 텍스트는 버린다. AWS 호출은 읽기 전용 가드가 걸린 점검 세션으로만 한다.
  - 마스킹 다리: LLM이 도구 입력에 쓴 자리표시자는 로컬에서 원래 값으로 바꿔 AWS를 호출하고, 도구 결과는 마스킹해 돌려준다. 전송 직전 차단 검사(`Masker.require_clean`)를 도구 결과에도 적용한다.
  - 조사 결과에는 status 필드가 없다 (원칙 1). "확인된 사실"마다 근거가 된 도구 호출 ID를 달고, 실제로 있었던 호출만 참조해야 검증을 통과한다. 판정은 바꾸지 않으며 REVIEW는 사람이 판단할 증적을 덧붙일 뿐이다.
  - 조사 하나당 도구 호출 수·반복·토큰 상한을 두고, LLM 응답·도구 호출·결과를 모두 조사 로그(`reports/investigations/`, 커밋 안 함)로 남긴다.
  - `kompass investigate` (예상 비용 확인, `--dry-run`), 보고서 "추가 조사 (참고)" 절. 같은 도구를 MCP 서버로 노출한다 (의존성 `mcp`는 해당 단위에서 승인).
  - 수동 항목 인터뷰는 이번 단계에서 partial·manual 항목별 증적 요청 목록까지만 만든다. 업로드 문서 검토(RAG)는 5단계로 미룬다.
  - Claude Managed Agents는 도구가 클라우드 컨테이너에서 실행되어 점검 자격증명을 클라우드에 두어야 하므로 쓰지 않는다 (로컬 읽기 전용 가드, 자격증명 미취급 원칙).
- 이유: 도구 결과는 처음 보는 식별자를 담으므로 응답 형태가 정해진 도구여야 마스킹 누락을 막을 수 있다. 사실·도구 호출 참조 검증은 3단계 인용 검증과 같은 방식으로 LLM 출력의 근거를 코드로 확인한다.
- 구현 기록 (2026-10-16):
  - `kompass investigate`는 비용 확인을 받은 뒤에 AWS 세션을 연다. 판정 결과의 계정과 같은 계정인지 검사하고(다르면 세션 오류로 중단), 판정 때와 같은 리전 범위를 쓴다.
  - 비용은 미리 셀 수 없으므로 "룰 수 × 룰당 토큰 상한 × 입력 단가"로 계산한 최대 비용을 보여준다.
  - 가드 위반(`ReadOnlyViolation`)은 조사 실패로 기록하지 않고 전체 조사를 세션 오류(종료 코드 3)로 중단한다. 조사가 하나도 성공하지 못하면 종료 코드 5.
  - 조사 결과는 해설과 같은 규칙으로 같은 판정 결과에만 보고서에 붙는다 (`AuditReport.with_investigations`). 보고서에는 사실·근거 호출 ID·도구 호출 표(원래 입력값)를 싣는다.
- 실습 계정 실행 기록 (2026-10-16, claude-opus-5-5, effort high, `--max-tokens 100000`):
  - 룰 16개(finding 28건) 모두 종료 사유 end_turn, 근거 검증됨 16·실패 0. 도구 호출 93회, 도구 오류 0. 입력 33만·출력 4.5만 토큰, 약 $2.24.
  - 도구 결과(마스킹 후)에서 계정 ID·리소스 이름·IP·액세스 키 ID 원문이 발견되지 않음.
  - 확인한 문제와 조치: (1) LookupEvents의 루트 사용자 `root`가 이름·ARN 경로로 가려져 "실제 루트인지 확인 필요"라는 불필요한 질문이 생김 → `root`를 마스킹 제외(AWS 고정 주체). (2) 모델이 자리표시자를 "MASKED_NAME_3·4"처럼 줄여 써 복원이 깨짐 → 조사 프롬프트·MCP 안내에 축약 금지 추가. 해설·종합 평가 프롬프트는 평가셋 기준선(ADR-033)에 묶여 있어 바꾸지 않음.
  - MCP 서버도 같은 계정에서 stdio로 연결해 판정 결과 조회·자리표시자 조회를 확인함 (원문 식별정보 노출 없음).

## ADR-036 읽기 전용 허용 목록 확대: LookupEvents, SimulatePrincipalPolicy
- 상태: 채택 (사용자 승인, 2026-10-15). 구현은 4단계 1단위.
- 결정: 읽기 전용 가드의 서비스 한정 예외에 `cloudtrail:LookupEvents`와 `iam:SimulatePrincipalPolicy`를 더한다. 접두어(`Lookup*`, `Simulate*`) 전체가 아니라 이 두 작업만 허용한다.
- 이유: 둘 다 대상 환경을 바꾸지 않는다. LookupEvents는 관리 이벤트 이력 조회(누가 언제 설정을 바꿨는지, 루트 사용 확인), SimulatePrincipalPolicy는 정책 평가 시뮬레이션(관리자 권한 여부를 실제 평가로 확인)이다. 에이전트의 추가 조사(REVIEW 판단 근거)에 필요하다. 이벤트의 사용자 이름·IP는 도구 계층에서 마스킹한다.

## ADR-037 증적 요청 목록: 고정 카탈로그
- 상태: 채택 (사용자 결정, 2026-10-16). 4단계 5단위.
- 결정:
  - 담당자 증적 요청은 LLM이 아니라 KISA 항목별 고정 카탈로그(`kompass/mappings/evidence_requests.yaml`)로 만든다. 요청마다 요청 증적·확인 목적·근거 원문 구절을 둔다.
  - 근거 구절은 원문 색인이 있는 환경에서 해당 항목 원문에 있는지, 형식 문구가 아닌지 테스트로 대조한다 (3단계 인용 검증과 같은 함수). 요청 문구 자체는 원문을 바탕으로 작성한 것이므로 항목마다 `verified: false`로 두고 보고서에 초안임을 표시한다 (원칙 7).
  - 대상: 자동화 분류가 partial·manual인 항목은 항상, full 항목은 결과가 확정되지 않았거나(검토 필요·확인 불가·점검하지 않음·수동 점검) 검토 필요·확인 불가 finding이 있을 때. 그 finding을 확인 대상 리소스로 붙인다. 취약(FAIL) finding은 증적이 아니라 조치 대상이라 붙이지 않는다.
  - 변경 (2026-10-16, 실습 실행 후): 처음에는 취약으로 확정된 full 항목을 모두 뺐으나, CA-03에서 IAM-003 취약 때문에 외부 IdP MFA 확인(IAM-009 검토 필요)까지 빠져 위 규칙으로 바꿈.
  - ISMS-P 통제항목 단위 요청은 만들지 않는다. 매핑이 초안이라 잘못된 통제에 증적을 요청할 수 있다.
  - 출력: 보고서의 "증적 요청 목록" 절(md)·"증적 요청" 시트(xlsx), 담당자에게 보낼 요청서 `kompass evidence`(`<점검 ID>.evidence.xlsx`, 담당자·제출일·제출 여부·비고 빈 칸). 요청서는 보고서 형식 `evidence`로도 만들 수 있다.
  - 카탈로그는 매핑 데이터에 포함해 `mapping_digest`에 반영한다.
- 이유: 증적 요청은 매번 같아야 하고(재현성), 원문 근거를 코드로 확인할 수 있어야 한다. 실제 리소스에 맞춘 문구 구체화는 비용 대비 효용이 낮고, 확인 대상 리소스 목록을 붙이는 것으로 대신한다. 제출된 문서의 검토(RAG)는 5단계에서 다룬다.

## ADR-038 MCP 서버
- 상태: 채택 (사용자 승인, 2026-10-16. 의존성 `mcp` 2.3 추가). 4단계 6단위.
- 결정:
  - `kompass mcp`가 stdio MCP 서버를 실행한다. 저수준 `mcp.server.lowlevel.Server`로 도구 스키마를 직접 등록한다 (조사 도구의 JSON 스키마를 그대로 쓰기 위해).
  - 도구: 판정 결과 조회 `kompass_findings`(상태·룰 필터, 페이지) + 조사 도구 12개(`agent/tools.py`). 모두 `read_only_hint`. 판정을 바꾸는 도구는 없다 (원칙 1).
  - MCP 클라이언트 뒤에는 LLM이 있으므로 에이전트 조사와 같은 마스킹 다리(`InvestigationToolbox`)를 쓴다 (원칙 5). 연결 하나가 마스커 하나를 공유해 세션 내내 같은 자리표시자를 쓴다. 지어낸 자리표시자는 거부하고, 가리지 못한 식별자가 남으면 결과 대신 차단 사실만 보낸다.
  - AWS 세션은 판정 결과와 같은 계정·리전 범위의 읽기 전용 점검 세션이다. 다른 계정이면 시작하지 않는다. 세션당 AWS 호출 상한(기본 50).
  - 읽기 전용 가드 위반은 도구의 버그이므로 그 뒤의 호출을 모두 거부한다 (서버는 살려 두어 클라이언트가 오류를 볼 수 있게 한다).
  - 호출마다 원래 입력값·마스킹한 결과를 `reports/mcp/<계정>/<점검 ID>.<시각>.mcp.jsonl`에 남긴다 (커밋 안 함).
  - 표준 출력은 MCP 통신 전용이므로 CLI 안내 메시지는 표준 오류로 낸다.
- 이유: 사용자가 쓰는 MCP 클라이언트에서 점검 결과를 대화형으로 조사할 수 있게 하되, 원칙 2·5를 서버 쪽에서 강제해야 클라이언트 설정과 무관하게 지켜진다.

- 상태: 채택 (사용자 결정, 2026-10-16). 5단계 첫 단위.
- 결정:
  - RDS collector가 점검 리전마다 `rds:DescribeDBInstances`·`rds:DescribeDBClusters`를 수집한다 (읽기 전용, 가드 허용 목록 변경 없음).

  - 읽기 전용 복제본은 RDS-004에서 해당 없음. AWS Backup 계획은 인정하지 않는다 (AWS Backup collector 이후).

- 이유: RDS는 KISA 항목 4개(그중 CA-11은 full)를 자동화해 수동 점검 항목을 9개에서 6개로 줄인다. Describe 응답 필드만으로 판정할 수 있어 결정론적 판정 원칙에 맞는다.

## ADR-040 VPC 흐름 로그 (VPC-003)
- 상태: 채택 (사용자 결정, 2026-10-16). 5단계 수동 점검 항목 자동화 ①.
- 결정:
  - EC2 collector에 `ec2:DescribeFlowLogs`를 더하고, VPC-003이 VPC별로 네트워크 인터페이스가 모두 활성 흐름 로그로 기록되는지 판정한다. VPC·서브넷·인터페이스 단위 흐름 로그를 모두 인정한다.
  - 트래픽 유형(ACCEPT·REJECT·ALL)과 전달 상태는 기관 정책이라 판정하지 않고 evidence에 남긴다.
  - KISA CA-14(인스턴스 로깅)에 매핑하되 근거 수준은 해석이다. 흐름 로그는 인스턴스의 네트워크 활동 기록이고, OS·애플리케이션 로그는 API로 확인할 수 없어 사람이 판단한다. 사용자 확인 전이라 `kisa_verified: false`.

- 이유: 기존 collector에 호출 하나만 더해 수동 점검 항목을 줄일 수 있다.

## ADR-041 GuardDuty 활성화·결과 알림 (GD-001~002)
- 상태: 채택 (사용자 결정, 2026-10-16). 5단계 수동 점검 항목 자동화 ②.
- 결정:
  - 새 collector `guardduty`가 리전마다 GuardDuty 탐지기(`ListDetectors`·`GetDetector`)와 기본 이벤트 버스의 GuardDuty 규칙(`events:ListRules`·`ListTargetsByRule`)을 수집한다. 알림 경로는 EventBridge에 있지만 룰은 스냅샷 하나만 보므로(ADR-015) 같은 스냅샷에 담는다. 이벤트 패턴의 `source`에 `aws.guardduty`가 없는 규칙은 저장하지 않는다.
  - GD-001: 리전에 활성 탐지기가 없으면 FAIL. GD-002: GuardDuty가 켜진 리전에서 GuardDuty 결과를 대상으로 보내는 활성 규칙이 없으면 FAIL, GuardDuty가 꺼진 리전은 N/A.
  - 알림의 실제 전달(SNS 구독 등), Security Hub·위임 관리자 경유 알림, CloudWatch 경보는 판정하지 않는다 (CA-19 `partial`).
  - KISA CA-19 매핑: GD-002는 직접, GD-001은 해석. 사용자 확인 전이라 `kisa_verified: false`. 탐지기 ID는 마스킹한다.
  - 실습 환경 `enable_guardduty`(기본 false). 기본값에서 GD-001 FAIL·GD-002 N/A를 실습 계정에서 확인했다.
- 이유: 모두 List/Get 호출이라 가드 허용 목록을 바꾸지 않고 CA-19를 자동화할 수 있다.

## ADR-042 S3 버킷 HTTPS 강제 (S3-007)
- 상태: 채택 (사용자 결정, 2026-10-16). 5단계 수동 점검 항목 자동화 ③.
- 결정:
  - S3 collector에 `s3:GetBucketPolicy`(정책 문서)를 더한다. 기존에는 공개 여부(`GetBucketPolicyStatus`)만 수집했다.
  - S3-007: 버킷 정책에 모든 주체·`s3:*`·객체(`버킷/*`)에 대해 `aws:SecureTransport = false` 요청을 거부하는 문장이 있으면 PASS. 정책이 없으면 FAIL, 정책 문서를 수집하지 못하거나 해석할 수 없으면 ERROR.
  - 최소 TLS 버전(`s3:TlsVersion`)과 ELB·RDS의 통신 암호화는 판정하지 않는다 (후보). 서버 원격 접근·데이터 이관 구간은 사람이 확인한다 (CA-12 `partial`).
  - KISA CA-12 매핑의 근거 수준은 해석(S3 API 통신을 리소스 접근 통신으로 봄). 사용자 확인 전이라 `kisa_verified: false`.
- 이유: 이미 수집하는 S3에 호출 하나를 더해 CA-12의 일부를 자동화할 수 있다. 정책 문서는 스냅샷(커밋 안 함)에만 남고, LLM에는 S3-007 evidence(문장 Sid)와 마스킹한 도구 결과만 간다.

## ADR-043 로그 보관 기간 (CT-002, LOG-001)
- 상태: 채택 (사용자 결정, 2026-10-16). 5단계 수동 점검 항목 자동화 (CA-17).
- 결정:
  - 기준값 `logs.min_retention_days` 기본 365일 (국내 접속기록 최소 1년 보관 요구에 맞춤, 기관이 조정).
  - CT-002: CloudTrail collector가 추적 버킷의 `GetBucketLocation`·`GetBucketLifecycleConfiguration`도 수집한다 (S3 호출이지만 룰이 스냅샷 하나만 보므로 같은 스냅샷에 담는다, ADR-015). 추적 로그 경로와 겹치는 활성 삭제 규칙이 기준보다 짧거나 날짜 지정이면 FAIL. 다른 계정 버킷(조직 추적)은 조회 거부로 ERROR.
  - LOG-001: 새 collector `logs`가 로그 그룹과, 보안 로그 대상을 알기 위한 추적(`DescribeTrails`)·흐름 로그(`DescribeFlowLogs`)를 함께 수집한다. 보안 로그 그룹(추적·흐름 로그 대상, `logs.security_log_group_prefixes` 기본 `/aws/rds/`)만 판정하고 나머지(Lambda 실행 로그 등)는 판정하지 않는다. 보존 기간 미설정(영구 보관)은 PASS, 대상 그룹이 없으면 FAIL.
  - 로그 백업·주기적 검토는 사람이 확인한다 (CA-17 `partial`). KISA 매핑은 직접 근거이나 사용자 확인 전이라 `kisa_verified: false`. 로그 그룹 이름은 마스킹한다.
- 이유: 전체 로그 그룹을 판정하면 보안과 무관한 FAIL이 많아 결과가 의미를 잃는다. 출처가 확인되는 보안 로그만 보고, 기관별 추가 대상은 설정으로 받는다.

## ADR-044 인스턴스·네트워크 권한 보유 주체 현황 (IAM-010~011)
- 상태: 채택 (사용자 결정, 2026-10-16). 5단계 수동 점검 항목 자동화 (CA-05·CA-06). 이로써 KISA 19개 항목 모두 자동 점검 룰이 하나 이상 있다 (partial 항목은 여전히 "검토 필요"가 상한).
- 결정:
  - 이미 수집하는 `GetAccountAuthorizationDetails`의 정책 문서를 정적으로 분석한다. `SimulatePrincipalPolicy`는 점검 collector에 쓰지 않는다 (원칙 2 예외를 넓히지 않음, ADR-036은 에이전트 조사 한정).
  - 대상 작업은 설정으로 받는다: `iam.instance_actions`(CA-05: 인스턴스 생성·삭제·시작·중지·속성 변경, SSM 세션·명령, EC2 Instance Connect), `iam.network_actions`(CA-06: 보안그룹·NACL·VPC·서브넷·라우팅·게이트웨이·피어링·EIP 연결, ELB, Route 53).
  - 주체: 사용자(직접·그룹 경유)와 역할. 서비스 연결 역할(`/aws-service-role/`)은 뺀다.
  - 근사: Action 와일드카드·NotAction은 해석하고, Resource·Condition·Deny·권한 경계는 판정에 쓰지 않는다 (보수적으로 권한 보유로 봄). 조건부·NotAction 경유 여부와 경계 ARN은 evidence에 남긴다. 본문을 모르는 관리형 정책은 `unknown_policies`.
  - 판정: 권한 보유 주체마다 REVIEW, 없으면 계정 PASS. 적절성 판단은 사람이 한다. KISA 매핑은 직접 근거이나 사용자 확인 전이라 `kisa_verified: false`.
- 이유: "적절하게 부여"는 결정론적으로 판정할 수 없으므로 현황 증적이 목적이다. 정적 분석은 과대 추정 쪽으로 틀리므로(놓치지 않음) 현황 보고에 맞다. 정확한 유효 권한이 필요하면 에이전트 조사가 시뮬레이션으로 확인한다.
- 실습 계정 확인 (2026-10-16): 그룹 경유 관리자 `kompass-lab-admin`이 두 룰 모두 REVIEW, SecurityAudit만 가진 `security_manager`와 서비스 연결 역할은 finding 없음.

## ADR-045 자격증명 보고서에 없는 사용자는 ERROR
- 상태: 채택 (2026-10-16, 실습 계정 확인 중 발견한 결함 수정). 원칙 3의 적용이라 사용자 결정 사항은 아니다.
- 문제: `GenerateCredentialReport`는 4시간 안에 만든 보고서를 다시 돌려준다. 실습 재배포 직후 스캔에서 10:19Z 보고서가 재사용되어 13:10Z에 만든 `kompass-lab-console-no-mfa`가 보고서에 없었고, IAM-003이 "콘솔 비밀번호가 있는 사용자가 없음(N/A)"으로 잘못 보고했다. 판정하지 못한 대상을 조용히 뺀 것이다.
- 결정: IAM-003·005·006은 권한 정보에는 있지만 보고서에 없는 사용자마다 ERROR("자격증명 보고서 생성 이후 확인된 사용자라 판정할 수 없음")를 낸다. evidence에 사용자 생성 시각과 보고서 생성 시각을 남긴다. 권한 정보를 수집하지 못했으면 대조할 수 없으므로 추가 finding을 내지 않는다.
- 이유: 데이터가 없다는 것을 "대상 없음"이나 양호로 보고하지 않는다 (원칙 3). 보고서 생성을 강제로 새로 할 방법은 없으므로 다음 점검에서 확인하도록 드러낸다.
