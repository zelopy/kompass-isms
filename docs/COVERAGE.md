# 점검 항목 분류표 (COVERAGE)

KISA 클라우드 점검 항목별로 kompass가 어디까지 자동으로 판정할 수 있는지 정리한다. 룰을 추가하거나 매핑을 바꿀 때 이 문서를 함께 갱신한다.

## 분류 기준

| 분류 | 뜻 | 항목 결과로 나올 수 있는 값 |
|---|---|---|
| `full` | 판단 기준 전체를 API 응답만으로 판정할 수 있다 | 취약 / 양호 / 확인 불가 / 해당 없음 |
| `partial` | 명백한 취약은 자동으로 판정하지만, 양호 판단에는 사람의 확인이 필요하다 | 취약 / 검토 필요 / 확인 불가 |
| `manual` | 자동으로는 판정하지 못하며, 증적 수집도 의미 있게 할 수 없다 | 검토 필요 |

KISA 판단 기준에는 "기관 정책에 따라", "주기적으로 검토", "목적에 맞게" 같은 표현이 많다. 분류는 아래 규칙을 따른다 (ADR-017).

- 기준에 설정값으로 확인할 수 없는 조건(주기적 검토 수행, 업무상 필요성, 인사 사유 등)이 있으면 `partial`.
- "기관 정책에 따라"라도 그 정책이 설정값으로 표현되는 경우(예: 읽기 이벤트 기록 여부, 보존 기간 일수)는 `kompass.yaml`로 기관 기준을 받아 판정하므로 `full`이 될 수 있다. 기본값은 일반적인 권고 수준으로 두고, 보고서에 적용한 기준값을 함께 표시한다.

**`partial` 항목의 판정 원칙 (ADR-013):** 룰은 명백한 위반(예: 0.0.0.0/0 SSH 개방)만 FAIL로 판정한다. 룰이 PASS를 내더라도 항목 결과는 집계 단계에서 "검토 필요"로 낮아진다. 따라서 `partial` 항목은 자동으로 "양호"가 되지 않는다. 사람이 확인하지 않은 기준을 충족했다고 보고하지 않기 위해서다 (ADR-005, ADR-010).

## 항목별 세부

판단 기준은 KISA 원문을 줄여 옮긴 것이다. 정확한 문구는 해당 쪽을 확인한다.

### CA-01 사용자 계정 관리 (상, 854쪽) — partial
- 기준: 불필요한 계정(퇴직·전직·휴직, 장기간 미사용)이 활성 상태이면 취약.
- 자동: 자격증명 보고서로 장기 미사용 콘솔 비밀번호·액세스 키를 판정한다 (IAM-005). 기간은 `iam.unused_credential_days`.
- 사람: 퇴직·전직 등 인사 사유로 불필요해진 계정인지 판단한다. kompass는 사용자 목록과 마지막 사용일을 증적으로 낸다.

### CA-02 사용자 정책 관리 (중, 855쪽) — partial
- 기준: 사용자·그룹에 목적에 맞는 역할·권한이 할당되어 있어야 한다. 원문 Step 2: "콘솔 최상위 관리자(최초 가입계정) 계정은 서비스 운영에 활용 금지".
- 자동: 루트 계정 액세스 키 존재(IAM-002)는 최상위 관리자 계정을 운영에 쓰는 명백한 사례로 FAIL. 사용자에게 직접 연결된 관리자 권한(IAM-007)도 FAIL.
- 사람: 그룹 경유 관리자 권한과 일반 권한의 적정성. IAM-007이 `REVIEW`로 현황을 낸다.
- 루트 계정 최근 사용(IAM-008)은 `REVIEW`로 현황을 낸다. 운영 목적 사용인지는 사람이 판단한다.

### CA-03 MFA 설정 (상, 856쪽) — full
- 기준: 각 계정별로 2차 인증이 설정되어 있으면 양호.
- 자동: 루트 계정 MFA(IAM-001), 콘솔 비밀번호가 있는 IAM 사용자 MFA(IAM-003).
- 참고: 콘솔 비밀번호가 없는 사용자(프로그래밍 방식 접근 전용)는 대상에서 뺀다. 원문의 "각 계정"을 콘솔 로그인 계정으로 해석한 것이며, 이 해석은 RULES.md에 명시한다.
- 외부 IdP: SAML·OIDC 공급자나 IAM Identity Center로 로그인하는 사용자는 IAM 사용자가 아니며, MFA는 IdP 쪽 설정이라 API로 확인할 수 없다. 이런 경로가 있으면 IAM-009가 `REVIEW`를 내므로 항목 결과는 "검토 필요"가 된다. 외부 IdP가 없는 계정에서는 IAM 룰만으로 양호를 판정할 수 있어 분류는 `full`로 둔다.

### CA-04 클라우드 계정 비밀번호 정책 관리 (중, 857쪽) — partial
- 기준: 복잡성을 만족하는 비밀번호 정책과 **로그인 시도 제한**이 모두 설정되어 있으면 양호. 복잡성은 영문자·숫자·특수문자 중 2종 조합이면 10자 이상, 3종 조합이면 8자 이상.
- 자동: `GetAccountPasswordPolicy`로 복잡성을 판정한다 (IAM-004).
- 사람: 로그인 시도 제한. **IAM 사용자 비밀번호 정책에는 로그인 실패 잠금 설정이 없다.** IAM Identity Center나 외부 IdP를 쓰는 경우 그쪽 설정을 사람이 확인해야 한다. 그래서 이 항목은 `full`이 될 수 없다.
- RULES.md와 차이: 현재 IAM-004는 "3종류 8자 이상"만 본다. KISA 기준(2종 10자 / 3종 8자)에 맞추려면 판정 로직과 설정 형식을 바꿔야 한다. AWS 정책은 대문자·소문자를 따로 요구하므로, KISA의 "영문자" 1종으로 묶어 세는 규칙도 정해야 한다.

### CA-05 인스턴스 서비스 정책 관리 (상, 858쪽) — partial
- 기준: 인스턴스 생성·접근 권한이 적절하게 부여되어 있으면 양호.
- 자동(후보): IAM 정책을 분석해 `ec2:RunInstances`, `ec2:*`, `ssm:StartSession` 등의 권한을 가진 사용자·역할 현황을 낸다.
- 사람: 그 권한이 적절한지 판단한다.

### CA-06 네트워크 서비스 정책 관리 (상, 859쪽) — partial
- 기준: 네트워크 서비스(방화벽, 로드 밸런서, DNS 등) 리소스 생성·접근 권한이 적절하게 부여되어 있으면 양호.
- 자동(후보): CA-05와 같은 방식으로 VPC·보안그룹·ELB·Route 53 쓰기 권한 보유 주체 현황을 낸다.

### CA-07 VPC 네트워크 서브넷 관리 (상, 860쪽) — partial
- 기준: 공개용 네트워크와 내부 네트워크가 분리되어 있으면 양호. 원문: "Public 서브넷은 인터넷 게이트웨이로, Private 서브넷은 NAT 게이트웨이로 할당하고 있는지 확인".
- 자동: 라우팅 테이블로 서브넷을 퍼블릭(IGW 경로)/프라이빗으로 분류한다. 리소스가 퍼블릭 서브넷에만 있는 VPC는 FAIL (VPC-001).
- 사람: 퍼블릭 서브넷에 있는 리소스가 공개용으로 의도된 것인지 판단한다.

### CA-08 가상 네트워크 리소스 관리 (중, 861쪽) — partial
- 기준: 내부용 리소스에 공인 IP가 없고 적절한 권한이 부여되어 있으면 양호.
- 자동: 공인 IP가 붙은 네트워크 인터페이스를 현황(`REVIEW`)으로 낸다 (VPC-002).
- 자동: `PubliclyAccessible=true`인 RDS 인스턴스는 FAIL (RDS-002).
- 사람: 공인 IP가 붙은 리소스가 내부용인지 판단한다.

### CA-09 접근 제어 설정 관리 (상, 862쪽) — partial
- 기준: 접근 제어 정책을 주기적으로 검토하고 불필요한 규칙이 없으면 양호. 원문은 방화벽 규칙과 보안그룹 규칙을 함께 예로 든다.
- 자동: 전체 개방(0.0.0.0/0, ::/0)된 관리 포트(SG-001), 전체 포트(SG-002), DB 포트(SG-003)는 불필요한 규칙의 명백한 사례로 FAIL.
- 매핑 제외: 기본 보안그룹 규칙(SG-004)은 이 항목에 매핑하지 않는다. AWS가 모든 VPC에 만드는 기본 규칙이라, 매핑하면 손대지 않은 계정에서도 항목이 항상 취약이 된다 (ADR-018).
- 사람: 주기적 검토 여부와 나머지 규칙의 필요성을 판단한다.

### CA-10 스토리지 리소스 퍼블릭 접근 관리 (중, 863쪽) — partial
- 기준: 스토리지 리소스에 불필요한 규칙이 없고 접근 제어 정책을 주기적으로 검토하면 양호. 조치 방법: "모든 인터넷 사용자 접근권한 차단".
- 자동: 계정·버킷 수준 퍼블릭 액세스 차단(S3-001, S3-002), 버킷 정책에 의한 퍼블릭 노출(S3-003).
- 사람: 주기적 검토 여부와, 퍼블릭이 아닌 접근 권한의 적정성을 판단한다.
- 자동: 버킷 ACL의 `AllUsers`·`AuthenticatedUsers` 대상 권한 부여(S3-006).

### CA-11 관계형 데이터베이스 암호화 설정 (중, 864쪽) — full
- 기준: 관계형 데이터베이스 암호화가 적용되어 있으면 양호. 원문 주석: 클라우드 암호화 기능은 스토리지·백업·스냅샷 암호화이고 테이블 단위 암호화가 아니다.
- 자동: `rds:DescribeDBInstances`, `rds:DescribeDBClusters`의 `StorageEncrypted` (RDS-001). Aurora·Multi-AZ DB 클러스터는 클러스터 단위로 판정한다.

### CA-12 통신구간 암호화 설정 (중, 865쪽) — partial
- 기준: 클라우드 리소스 간 통신 구간에 암호화가 적용되어 있으면 양호. TLS 1.2 이상, TLS 1.3 권장.
- 자동(후보): ELB HTTP 리스너와 오래된 TLS 정책, S3 버킷 정책의 `aws:SecureTransport` 강제 여부, RDS 파라미터 그룹의 SSL 강제 설정.
- 사람: 서버 원격 접근, 데이터 이관 경로 등 API로 보이지 않는 구간.

### CA-13 클라우드 서비스 사용자 계정 로깅 설정 (상, 866쪽) — full
- 기준: 사용자 계정 로깅이 기관 정책에 따라 설정되어 있으면 양호.
- 자동: `cloudtrail:DescribeTrails`, `GetTrailStatus`, `GetEventSelectors`로 멀티 리전 추적, 로깅 활성 상태, 관리 이벤트(읽기·쓰기) 기록을 판정한다.
- "기관 정책"은 설정으로 받는다: 읽기 이벤트 기록 요구(`cloudtrail.require_read_events`, 기본 true). 로그 전달 오류(`LatestDeliveryError`)는 증적으로 남긴다.

### CA-14 인스턴스 로깅 설정 (중, 867쪽) — partial
- 자동(후보): VPC Flow Logs 활성화.
- 사람: 인스턴스 OS·애플리케이션 로그 수집 여부와 주기적 검토.

### CA-15 관계형 데이터베이스 로깅 설정 (중, 868쪽) — partial
- 자동: RDS `EnabledCloudwatchLogsExports`가 비어 있으면 FAIL (RDS-003).
- 사람: 엔진별로 필요한 로그 종류(감사·오류·느린 쿼리 등)가 기관 정책에 맞는지와 주기적 검토.

### CA-16 오브젝트 스토리지 버킷 로깅 설정 (중, 869쪽) — full
- 기준: 버킷 로깅이 기관 정책에 따라 설정되어 있으면 양호.
- 자동: S3 서버 액세스 로깅(S3-005).
- CloudTrail S3 데이터 이벤트로 버킷 접근을 기록하는 경우: 룰은 하나의 서비스 스냅샷만 본다는 원칙을 유지해 S3-005에서는 인정하지 않는다. 데이터 이벤트를 쓰는 조직에서는 FAIL이 나올 수 있으며, 4단계 에이전트가 CloudTrail 설정을 추가 조사해 해석에 반영한다 (ADR-015). 이때도 status는 바꾸지 않는다.

### CA-17 로그 보관 기간 설정 (중, 870쪽) — partial
- 자동(후보): CloudWatch Logs 로그 그룹 보존 기간, CloudTrail 로그 버킷 수명주기 규칙을 설정 기준값과 비교한다.
- 사람: 보관 정책 자체의 수립 여부, 로그 백업.

### CA-18 백업 사용 여부 (중, 871쪽) — partial
- 자동: RDS 자동 백업 보존 기간이 `rds.min_backup_retention_days`(기본 7일) 미만이면 FAIL (RDS-004).
- 자동(후보): AWS Backup 계획과 보호 대상 리소스.
- 사람: 백업·복구 절차 수립과 주기적 검토.

### CA-19 가상 리소스 이상징후 알림 설정 (중, 872쪽) — partial
- 자동(후보): 리전별 GuardDuty 활성화.
- 부분: GuardDuty 결과를 EventBridge·SNS로 전달하는 알림 경로, CloudWatch 경보 존재 여부.
- 사람: 알림이 실제로 담당자에게 전달되는지.
